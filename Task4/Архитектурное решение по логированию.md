Задание 4. Логирование

1. Логи

- CRM API (Spring Boot) отвечает за переход заказа в производство
- MES API (C#) ключевой сервис расчета стоимости, часто зависает
- Shop API (Spring Boot) точка входа для всех заказов

- RabbitMQ интеграционная шина, где теряются сообщения

Примеры логов уровня INFO:

Пользователь {user_id} создал заказ {order_id}
Файл по заказа {order_id} типа 3D-модель загружен успешно
Статус заказа изменен с {old_status} на {new_status} в {system}
Заказ {order_id} сообщение отправлено в очередь {queue_name}
Заказ {order_id} сообщение получено из очереди {queue_name}

Другие уровни логирования:
- FATAL полный отказ сервиса 
- DEBUG только в dev средах, для отладки логики
- ERROR исключения, невозможность изменить статус, ошибки расчета
- WARN некритичные сбои (например, повторная отправка в очередь)

2. Мотивация (использование централизованного логгирования)

- Важно быстро находить причину зависших заказов
- Отфильтровывать заказы с долгим расчетов, для выделения расчетов со сбоем
- Определять подтверждение получения сообщений в RabbitMQ

Улучшаемые Метрики:
- Улучшение взаимодействия по API с партнерами (SLA по заказу < 1 часа).
- Снижение нагрузки на поддержку при инцидентах, меньше ручных разборов и привлечения специалистов. 
- Время реакции на жалобы клиентов (с суток до ~10 минут).
- MTTR (Mean Time To Resolve) инцидентов, а именно среднее время восстановления после сбоя работы системы.
- Процент зависших заказов, в идеале прийти к 0% зависших заказов.

3. Предлагаемое решение

OpenSearch + Filebeat + Kibana
Причина выбора - бесплатная лицензия, совместимость с ELK, хорошая поддержка в облаке

- OpenSearch хранение и индексация
- Filebeat на каждом инстансе API и RabbitMQ для сбора логов
- Kibana визуализация и поиск

4. Политика безопасности

- В логи не попадают пароли, токены, email, ФИО, номера карт
- Отстутсвует доступ у фронтендеров и внешних пользователей
- Все чувствительные поля заменяются на Guid на уровне приложения
- Доступ к Kibana только через SSO с ролями (Devops, Бэкенд-разработчики, поддержка пользователей)


5. Политика хранения

- Отдельный индекс на сервис: shop_api_YYYY_MM_DD, mes_api_YYYY_MM_DD и тд
- Размер: ~2 ГБ день на сервис (оценка по текущему RPS)
- Хранение 30 дней для Publish, 7 дней для Develop/Release
- Автоматическое удаление средствами политики ILM в OpenSearch

6. Анализ и алертинг

Алерты в Kibana
- ERROR FATAL логи
- Отсутствие логов создания заказа > 10 мин 
- Резкий рост INFO: Большое количество заказов создано (>1000/мин) подозрение на DDoS или на инцидент связанный с ошибкой системы
- Алерты регистрировать в TaskManager + автоматический саппорты в TaskManager

7. Приоритеты

- 1. MES API (Определение тех, которые потенциально привели к падению)
    * Cамые продолжительные операции
    * Частые зависания
- 2. RabbitMQ (Причина зависших заказов)
    * Основной канал между MES и CRM
    * Потерянные сообщения 
- 3. Shop API
    * точка входа всех заказов
