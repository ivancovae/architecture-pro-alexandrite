Задание 5. Кеширование

1. Мотивация

Операторы MES жалуются, что страница со списком заказов загружается медленно, несмотря на пагинацию и фильтрацию. Это напрямую влияет на их мотивацию кто первым берет заказ тот получает оплату

Проблема вызвана тем, что каждый запрос списка заказов идет напрямую в MES DB, а запросы на чтение списка часто совпадают по пользователям и статусам, поэтому стоит использовать кеширование.

Использование кеширования поможет:
- Формировать списка новых заказов, что ускорит отображение списка новых заказов для операторов
- Распределит и снизить нагрузку на MES DB
- повлияет на улучшение производительности MES UI и UX

Объект кеширования
Списоки заказов (с фильтром по статусу и пагинацией), получаемый из MES API

2. Предлагаемое решение
Тип кеширования- Серверное (в MES API)

Почему не клиентское
- MES UI внутреннее SPA приложение, запускаемое на разных устройствах
- Клиентское кеширование не воздействует на проблему первоначальной загрузки и не снижает нагрузку на MES БД

Паттерн кеширования Write-Through

Почему Write-Through
Изменение статуса повлияет на обновление в БД и в кеше в рамках одной транзакции
Даже при потере события из очереди кеш будет актуален и заказы будут исполнены, потому что обновление идёт напрямую из MES API, а не асинхронно.

Альтернативы
- Read-Through требует сложной настройки кеша как прокси
- Refresh-Ahead избыточен заказы появляются редко (до +100 в месяц), если бы была постоянность это был бы вариант для использования
- Write-Through/Write-Behind не нужны, так как запись списка заказов влияет на обновление статуса, а это редкая операция и не касается кешируемого списка

3. Диаграмма последовательности
Оператор использует MES UI использует MES API обращается к кеш (Redis) если промах обращается к MES DB если нет то возвращает значение из кеша

| Сценарий | Действие в MES API |
|---|---|
|    Оператор берёт заказ        | а. Обновить статус в MES DB б. Синхронно очистить, после перестроить кеш                                          |
| Статус обновлён через RabbitMQ | а. Обновить статус в MES DB б. Синхронно очистить, после перестроить кеш связанный с предыдущим и новым статусом  |


4. Стратегия инвалидации кеша
    * Программная инвалидация (Основаная, при любом изменении статуса заказа)
    * временная (TTL>=60сек) (Вторичная, TTL как запасной вариант, если инвалидация не сработала)

TTL>=60сек все еще допускает показ устаревшего списка, очищение по событию дает максимальную актуальность, защита от ошибок, если событие пропущено TTL обеспечит обновление.
